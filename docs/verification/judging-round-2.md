## P1-01 — 현재 장소가 바뀐 공지를 이전 행사장으로 확정

발견 시점에 브라우저와 JS 엔진 모두에서 직접 재현했다.

1. ‘안내문에서 장소 찾기’를 연다.
2. `코엑스 오디토리움에서 진행하던 행사를 송도컨벤시아로 옮겼습니다.`를 입력한다.
3. 높이 `1.65`, 높이 확인, 안전 주차 확인을 입력한다.
4. 앱은 ‘공식 시설 안내와 일치하는 장소를 찾았습니다’라고 표시하고 확정 버튼을 활성화한다.
5. 확정하면 **코엑스 오디토리움 · 북문 · B3 블루존**이 표시된다.

엔진에서 다음도 `ready`, `canConfirm: true`였다.

| 입력 | 잘못 허용된 결과 |
| --- | --- |
| `코엑스 오디토리움 3층. 실제 행사장은 송도컨벤시아입니다.` | 오디토리움 확정 가능 |
| `코엑스 오디토리움 3층 행사는 DDP 아트홀에서 진행합니다.` | 오디토리움 확정 가능 |
| `코엑스 오디토리움 3층 행사가 다른 곳으로 이동됐습니다.` | 오디토리움 확정 가능 |
| `COEX auditorium event has moved to Songdo Convensia.` | 오디토리움 확정 가능 |
| `COEX auditorium 3F event cancelled` | 취소된 행사 확정 가능 |

원인은 발견 당시 `extractDestinations()`의 제한된 타시설·변경 정규식과, 지원 장소명이 한 번 등장하면 유효한 현재 행사장으로 취급하는 방식이다. Kotlin `BriefEngine.resolve()`에도 같은 종류의 제한된 패턴이 있었다. Kotlin 런타임에서 위 문장을 실행한 것은 아니므로 동일 결과를 실기 확인했다고 쓰지 않는다.

수정: 두 엔진에 동일 회귀 사례를 넣고, 이동·옮김·영문 취소/이전·추가 시설 주장 시 보류해야 한다. 시설명 블랙리스트만 늘리는 방식에는 한계가 있으므로, 서로 다른 ‘행사장’ 주장이나 현재/이전 장소를 명확히 분리하지 못하면 현재 유효한 한 문장을 선택·확인하는 흐름으로 돌려야 한다. 높이·주차 체크만으로 행사장 판정이 검증된 것처럼 보이면 안 된다. 수정 담당자에게 즉시 전달했다.

## P1-02 — 차량의 ‘돌아올 때 내 차’ 효용이 기기 경계에서 끊김

이는 숨겨진 동기화 버그가 아니라 **구현된 제품 범위의 핵심 가치 공백**이다. 소스와 제품 범위에서 확인했다. 실차에서 이 동선을 실행한 것은 아니다.

재현 시나리오: 차량 APK에 실제 주차 위치를 저장→차에서 내려 행사 참가→차 밖에서 차량을 찾기 위해 휴대폰을 연다. 휴대폰에는 차량에 기록한 메모가 없으며, 위치 공유·전달·동기화가 없다. 차량 화면을 다시 읽으려면 이미 차량으로 돌아와야 한다. 휴대폰 웹에 따로 기록하는 대안은 가능하지만 사용자가 같은 방문 정보를 다시 적어야 한다.

수정: 실제 휴대폰 전달과 차 밖 재열람을 구현·검증하거나, 현재 차량 기능의 핵심가치를 ‘출발 준비와 차 안의 주차 기록’으로 좁히고 휴대폰 웹 기록을 별도 사용 흐름으로 명확히 보여야 한다. 후자는 설명 정확도를 높여도 차량에서의 귀환 효용 자체를 채우지는 않는다. 랜딩의 동기화 부재 고지는 확인했으며, 고지 자체를 기능 점수로 가산하지 않았다.

## P2-01 — 여러 장소를 선택하라는 안내 뒤 선택해도 층이 모두 충돌

`코엑스 오전 그랜드볼룸 1층, 오후 오디토리움 3층`을 넣으면 여러 장소이므로 방문할 장소를 선택하라고 한다. `auditorium`을 선택해도 `buildBrief()`는 전체 안내문의 1층까지 오디토리움 3층과 대조하여 `needs_review`로 막는다. `코엑스 오디토리움 3층. 1층 로비에서 등록해주세요.`도 행사장 층이 틀렸다고 처리한다.

안전하게 보류하는 것은 타당하다. 다만 정상 안내문을 공유해 얻는 편의가 떨어지고, 첫 안내인 ‘장소 선택’만으로 해결되지 않는다. 선택 장소와 연결된 문장·층을 보여주거나, 처리하지 못한 구절을 구체적으로 표시해 사용자가 무엇을 확인·제거해야 하는지 알려야 한다. 층 검증 자체를 제거하면 안 된다.

## P2-02 — Android 자료 상충에서 구체적인 대조 값이 보이지 않음

코드 기준: 컨퍼런스룸 E를 선택하고 높이를 입력하면 Android는 자료가 다르므로 확정할 수 없다는 설명과 접힌 출처 영역의 두 링크를 제공한다. 그러나 웹의 ‘일반차량 안내 B2 퍼플존 / 공지 B2·B3·B4 블루존’처럼 **어떤 값이 다른지**를 화면 안에서 대조하지 않는다. `MainActivity.render()`의 `source_conflict` 분기와 `sources.text`에서 확인했다. Android 실화면 재현은 아직 없다.

수정: 브리핑 패널에 출처명·확인일·각 추천 구역을 함께 읽을 수 있게 표시하되, 추천 동선으로 보이지 않도록 확정 보류 상태를 유지한다. 현재 Android의 안전 보류는 인정하지만 웹과 동일한 근거 검토 경험으로 평가할 수 없다.

## 시각·사용성 판단

데스크톱 첫인상은 명료하다. 랜딩의 ‘갈 때는 어느 문, 돌아올 땐 내 차’와 건물·주차 장면은 목적을 빨리 전달한다. 앱 화면의 입력 영역과 도착 패스가 구분되고, 확정 뒤 북문/B3 같은 핵심 정보는 크게 읽힌다. 주차 메모는 녹색 표지와 별도 영역으로 추천 구역과 구분된다. 동일한 카드가 반복되는 단조로운 화면은 아니며, 입력 영역의 구분선과 한 개의 큰 패스가 시각적 역할을 가진다.

남은 약점은 디자인 장식보다 정보의 우선순위다. 전체 화면의 친근한 그림에 비해 차량 이용자가 반드시 이해해야 할 기기 간 단절은 작은 보조 문구다. 핵심 제목의 기대가 실제 차량 기능보다 크다. 지원 범위가 5개 안내/3개 보류라는 점도 목록 선택 이전에 더 분명하면 불필요한 입력을 줄일 수 있다. 정상 안내문을 재편집해야 하는 오류 상태는 구체적 수정 위치를 안내해야 한다.

모바일과 큰 글씨는 현재 CSS에 한 열 전환·줄바꿈·최소 터치 크기·동작 줄이기 대응이 존재한다. 그러나 이것만으로 최신 버전의 잘림·가로 스크롤·키보드 겹침·스크린리더 읽기 순서가 통과했다고 판단하지 않았다. Android의 64dp 버튼과 sp 텍스트도 실제 큰 글씨 검증을 대체하지 않는다.

## 남은 제출 완성도

현재 결과는 작동하는 도착 준비 웹과 비교적 보수적인 차량 입력 구조다. 수상 경쟁력을 높이려면 P1 안내문 오확정의 회귀 검증, 최신 APK의 공유→확정→실제 메모→재실행 기록, Pleos 상태 전환의 실제 증거, 차 밖 재열람을 포함한 가치 검증이 필요하다. 랜딩의 두 영상은 0.5.0 웹 기록으로 명시되어 있어 정직하지만, 이번에 새로 내세운 공유수신·주차 메모를 보여주는 최신 제품 증거는 아니다.

실제 사용자 인터뷰·현장 시간 절감·방문 간 재사용률·사업 제휴는 아직 없다. 해당 공백은 문서 표현 수정이나 단위시험 수 증가로 채울 수 없다. 다음 심사는 수정된 구현과 새로 확보한 증거만으로 다시 점수를 산정해야 한다.
